# ローカルAI環境自動構築ツール 企画書と設計計画（RTX Spark版）

- 文書版：3.2
- 作成日・更新日：2026年10月28日
- 対象：企画者、開発担当者、評価担当者。
- 状態：企画・設計案。実装、導入、実機検証は未実施。導入作業はユーザーの「開始」指示まで行わない。
- 本版は v2.2 を **NVIDIA RTX Spark（128GB 統合メモリ）搭載機1台での個人利用** に絞って作り直したものである。多機種・多OS対応、外部アプリ接続、実測による構成の自動探索は範囲から外し、RTX Spark 固有の条件と、v2.2 で抜けていた前提を追加した。
- 「確定要件」はユーザー指定、「設計方針」は実現方法の提案、「要検証」は P0 で実機確認する事項を示す。外部情報は 2026年10月28日時点で確認できた範囲であり、出典は16章に置く。

## 1 企画の結論

**RTX Spark 搭載PC上で、ユーザーが選んだ目的別環境を自動構築し、一つの対話画面から理解・生成・修正まで行えるツールを作る。**
環境は「推論」「画像生成」「音声生成」「動画生成」の四つとする。
対象機を1機種に固定することで、診断・構築・検証の対象を絞り、各環境を「事前に検証した固定構成のカタログ」から構築する方式にする。
品質を最優先、速度を次点とし、ユーザーが決めたメモリ予算を守る。Ollama は使わず、ロード・推論・メモリは本ツールが直接管理する。

### 1.1 利用者と提供価値

- 利用者はユーザー本人1人。配布・販売はしない（ライセンス判断はこの前提で行う。13章）。
- インストール、依存関係、モデル取得、起動設定を人が調べて組み合わせる手間をなくす。
- 添付、相談、生成、確認、修正依頼、保存を同じ画面で行える。
- できること・できないこと・今何を待っているかを常に表示する。
- 構成を勝手に切り替えず、128GB 統合メモリを使い切らずに他の作業の余裕を残す。

- RTX Spark 以外の機種への対応。

- 外部アプリ（Claude Code、ChatGPT 等）からの利用。
- 音楽・効果音の生成（E3 は読み上げ・話し声に限る）。
- クラウドへの送信や代替処理。

## 2 対象機：RTX Spark の前提

### 2.1 確認できた仕様

| 項目 | 内容 | 本計画への影響 |
|---|---|---|
| チップ | GB10 系 SoC（Arm CPU 最大20コア＋Blackwell GPU 最大6,144 CUDAコア）、CPU・GPU は NVLink-C2C で接続 | CPU は Arm64。x86 前提のパッケージは動かないか、エミュレーションになる |
| メモリ | LPDDR5X 統合メモリ 128GB（ユーザーの機体）。帯域は約300GB/s（報道値） | 128GB 機のみを対象とする。32GB モデルは対象外 |
| OS | Windows 11 on Arm。x86 アプリは Prism エミュレーションで動く。NVIDIA は WSL での開発にも言及 | 実行基盤の選択が必要（2.2節） |
| 発売 | 2026年5月発表、10月にノート発売、11月に小型デスクトップ | 実績が少なく、情報が出揃っていない |
| ドライバ・CUDA | 開発者向けドライバ 616.00（プレビュー）、CUDA 13.4（Windows Arm64 対応はプレビュー） | ドライバとCUDAの版を固定し、更新は別承認・再検証とする |
| 既知の不具合 | PyTorch の連続実行で GPU タイムアウトが起き、無応答・再起動に至ることがある（調査中）。ページング可能メモリ経由の転送が遅い | 長時間生成中の GPU タイムアウトを最重要リスクとして扱う（12章） |
| ソフト対応 | NVIDIA は Windows on Arm 向け初の PyTorch-CUDA ビルドと、主要 Python パッケージの97%超の Arm 版を発表。llama.cpp は Windows ML バックエンド対応に言及 | llama.cpp の CUDA ビルド、ComfyUI、Diffusers、音声・動画系の Arm64 Windows 対応は**公開情報では未確認** |
| 電力 | ノート 45〜80W、デスクトップ 140W | ノートではバッテリー駆動時に速度・安定性が変わる |

### 2.2 実行基盤の選択（要検証、P0 で決定）

RTX Spark では、AI エンジンを動かす場所に二つの候補がある。

| 案 | 内容 | 利点 | 懸念 |
|---|---|---|---|
| A：WSL2（Arm64 Linux） | エンジン群を WSL2 内の Ubuntu Arm64 で動かし、UI は Windows 側のブラウザで開く | DGX Spark（同じ GB10・Arm64 Linux）向けの手順・ビルド・実績を流用できる。Python 依存の互換性が高い | WSL2 内で CUDA が使えるかが未確認。WSL2 のメモリ上限設定と Windows 側の使用量の二重管理が要る。ファイル共有の速度 |
| B：ネイティブ Windows Arm64 | エンジン群を Windows 上で直接動かす | 余計な層がなく、メモリ管理が一本化される | llama.cpp の CUDA ビルド、ComfyUI のカスタムノード、音声・動画系パッケージの Arm64 Windows 版が揃っていない可能性 |

**設計方針：** P0 で両案を実機で試し、四環境の必須エンジンが揃う方を主経路にする。エンジンごとに混在させることは許すが、メモリ予算は一つの物理メモリとして一元管理する。x86 エミュレーション（Prism）上で GPU 処理を動かす構成は採用しない。

### 2.3 統合メモリの予算

- 128GB 機の初期値の例：OS・他アプリ用に 32GB を残し、AI 用予算 96GB。ユーザーが導入時に変更できる。
- 予算は重みだけでなく、KV キャッシュ、画像・音声・動画の展開、VAE・エンコーダー、一時領域、ロード時の二重確保を含める。
- GPU から確保できる上限、WSL2 の上限（案Aの場合）、OS の実使用量はそれぞれ異なりうるので、P0 で実測する。スワップを GPU 用の容量として数えない。
- 厳密な上限の強制はできない前提で、「実測ピーク×安全係数」で受付を判定する。超過が見込まれる依頼は実行前に止め、入力削減や出力上限の変更を提案する。無断で品質を下げない。

## 3 四つの環境

| 環境 | 必須の入力理解 | 必須の出力 | 利用例 |
|---|---|---|---|
| E1 推論 | テキスト、画像、音声、動画（音声を含む） | 対話回答・推論結果 | 図を説明する、録音の内容を相談する、動画の指定区間を考察する |
| E2 画像生成 | テキスト、画像 | 対話と画像生成・参照画像の編集 | 参考画像を見せ、相談しながら作り直す |
| E3 音声生成 | テキスト、音声 | 対話と日本語音声の生成 | 参考音声の話し方を相談し、指定文章を読み上げさせる |
| E4 動画生成 | テキスト、画像、動画（音声を含む） | 対話と画像を元にした短い動画の生成 | E2 で作った画像を元に5〜10秒の動画を作る |

- E2〜E4 では対話モデルが窓口となり、許可されたツールとして理解・生成エンジンを呼ぶ。
- 環境は人が選ぶ。環境外の依頼には非対応と理由を伝え、切替時の取得量と待ち時間を示し、ユーザーが選ぶまで切り替えない。
- 未導入の環境は必要になったときに構築する。初回に四環境すべてを取得しない。
- 生成動画に音声が付くかは構成の能力として表示し、無音出力を隠さない。
- 日本語での対話・理解・読み上げを必須とする。

### 3.1 E1 の構成方針

「推論の質」と「何でも読めること」を両立させるため、E1 は二段構成を基本とする。

1. **推論モデル**：テキストの推論と最終回答を担う大型モデル。
2. **理解モデル**：画像・音声・動画を読み、時刻付きの観察結果を推論モデルに渡す中小型のマルチモーダルモデル。

一つのモデルで全てを兼ねる構成（例：Qwen3-Omni）も候補として P0 で比較し、品質が同等なら単一構成を選ぶ。二段構成では、理解モデルの観察結果を経由した回答であることを回答時に表示する。

### 3.2 動画とその音声の理解

llama.cpp の動画入力（2026年6月追加）は当初は映像フレームのみだった。2026年10月28日時点の最新版（llama-server の `input_video`）では、音声トラックまで聞けるのは LFM3-Omni だけである（[server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)）。このため、音声トラックを聞けるモデルには切り出した動画をそのまま渡し、それ以外のモデルでは次の方式をとる。

1. ffmpeg で動画を検査し、映像フレーム列と音声トラックに分ける（ffmpeg は llama.cpp に同梱されないので本ツールが用意する）。
2. 時間区間ごとに、フレーム列と同じ区間の音声を、画像と音声の両方を受けられるモデル（Qwen3-Omni、Gemma 4 E4B 等）へ一つのプロンプトで渡す。
3. 区間ごとの時刻付き結果を作り、全体要約へまとめる。
4. この方式で音声と映像の関係を十分に説明できない場合は、文字起こしと音響イベント検出を補助として使い、その旨を回答前に表示する。

LFM3-Omni（カタログ `e1-lfm3-omni`）と上記の分離方式を P0 で比較し、品質の良い方を標準にする。

## 5 システム構成と UI

```text
ユーザー（Windows 側ブラウザ）
  └─ 対話UI（添付・プレビュー・履歴・環境選択・進捗・取消）
       └─ ローカル制御サービス（ループバックのみ）
            ├─ 構築：機器確認・カタログ選択・取得・検証・起動
            ├─ 会話管理・許可済みツール呼出し
            ├─ ジョブ管理・推論ロック・メモリ受付判定・GPU監視
            ├─ 対話／推論：llama.cpp（llama-server）
            ├─ 理解：llama.cpp のマルチモーダル＋ffmpeg 前処理
            ├─ 生成：画像・音声・動画の専用エンジン（ComfyUI 等）
            └─ 共通成果物フォルダ・設定・カタログ・測定結果
```

**UI の設計方針：** まず既存の OSS チャット UI（例：Open WebUI。OpenAI 互換の llama-server に接続でき、Ollama なしで使える）を制御サービスの前に置く案を P0 で試す。添付・画像表示・音声/動画再生・長時間ジョブの進捗表示・取消が満たせない場合に限り、独自 UI を作る。どちらの場合も Ollama 連携機能は無効化し、使わない。

- 生成エンジンは共通の口（能力照会、起動、実行、取消、結果取得、停止）で包む。
- 制御サービスは Windows ログイン中のユーザー権限で動かす。OS の自動起動は設定しない。

## 6 自動構築

### 6.1 構築の流れ

1. 機器確認：RTX Spark（128GB）であること、ドライバ・CUDA の版、空きディスク、電源状態、実行基盤（2.2節で決めた方式）が使えるかを確認する。条件外なら理由を表示して止める。
2. 計画表示：選んだ環境のカタログ構成、取得先、ライセンス、容量、必要な権限、所要時間の目安、撤去方法を表示し、承認を得る。
3. 隔離された作業ディレクトリと依存環境を作る。既存のドライバやユーザー環境は無断で置き換えない。
4. 公式配布元からモデルとエンジンを取得し、ハッシュとサイズを確認する。中断した取得は再開する。
5. エンジンを固定バージョンで準備し、設定を生成する。
6. 健全性試験（短い入力で全必須能力を一回ずつ）と、速度・ピークメモリの測定を行う。
7. 合格した環境だけを「使用可能」にし、能力一覧・制約・測定結果を保存する。

- 管理対象ファイルだけを消すアンインストールと、一つ前の構成へ戻す手段を用意する。
- ドライバ・CUDA・WSL2 の導入や更新が必要な場合は、理由を示して別に承認を得る。プレビュー版ドライバの更新は再検証の対象とする。

### 6.2 ディスク容量の見積もり（要検証）

| 対象 | 目安 |
|---|---|
| E1（推論モデル＋理解モデル） | 80〜130GB |
| E2（画像生成・編集モデル＋対話モデル） | 40〜80GB |
| E3（TTS＋音声理解） | 10〜30GB |
| E4（動画生成モデル＋テキストエンコーダー＋理解モデル） | 60〜120GB |
| エンジン・依存環境・キャッシュ | 30〜60GB |
| 合計 | 約220〜420GB＋生成物 |

構築前に空き容量を確認し、不足時は環境ごとに導入を分けるよう提案する。

## 7 構成カタログとモデル選定

### 7.1 選定の考え方

- 各環境の構成は、開発者が RTX Spark 実機で検証した固定構成として「カタログ」に登録する。カタログはコードと分けたデータとし、モデル更新時に差し替えられるようにする。
- 各環境に「標準構成」と、ユーザーが予算を小さくした場合の「軽量構成」の最大2種を用意する。
- 構築時の実測は「速度・ピークメモリ・必須能力の合否」を測ってユーザーに見せるためのもので、多数の候補を自動で探索・採点するものではない。
- 画像・音声・動画の品質は自動採点で決めない。カタログ登録時に開発者が基準付きで確認し、ユーザーは生成結果を見比べて構成を選べる。
- 順位は「必須能力・安全・メモリ上限への合格」→「品質」→「同等品質内の速度」とする。

### 7.2 精度と量子化のルール

- **禁止：** 本ツール自身による量子化・再量子化、KV キャッシュ精度の無断変更、暗黙の精度変換。
- **許可：** 配布元が公式に出している形式（例：gpt-oss の MXFP4、LTX の公式 FP8）は「配布元の形式」として候補にしてよい。その旨を表示する。
- **要承認：** 第三者が量子化した配布物（コミュニティ GGUF 等）を使う構成。導入時の初期設定で、ユーザーが一括で許可・不許可を選べるようにする。
- 配布元の型・実行時の型・キャッシュの型を記録し、確認できるようにする。

### 7.3 初期候補（要検証。P0 で RTX Spark 実機と日本語で確認する）

| 環境 | 役割 | 候補 | 備考 |

| E1 | 推論モデル | gpt-oss-120b（MXFP4、配布元形式） | DGX Spark で生成約46 tok/s の報告あり。日本語品質は要確認 |
| E1 | 理解モデル | Qwen3-Omni-30B-A3B、Gemma 4 E4B | llama.cpp で画像＋音声入力に対応。単一構成の候補も兼ねる |
| E2 | 対話・画像理解 | Gemma 4（26B-A4B または 31B） | llama.cpp で画像入力対応 |
| E2 | 画像生成・編集 | Qwen-Image／Qwen-Image-Edit 系、FLUX 系 | FLUX.1 dev は非商用ライセンス（個人利用前提なら可） |
| E3 | 音声理解 | Gemma 4 E4B、Qwen3-Omni、Qwen3-ASR | llama.cpp の音声入力 |

| E4 | 理解 | E1 の理解モデルを共用 | 3.2節の方式 |

## 8 実行制御とメモリ管理

- 対話モデルは構造化されたツール呼出しだけを出し、制御サービスが引数・範囲・権限を検証してから実行する。対話モデルの文章を直接シェル実行しない。
- 全エンジンで推論ロックを共有し、補助モデル（ASR、エンコーダー、VAE 等）を含めて推論は一つずつ実行する。常駐は予算内で許可する。
- 対話モデルがロックを持ったまま生成完了を待つ構造は禁止する。順序は「対話モデルがツール呼出しを出してロック解放 → 生成ジョブがロック取得・実行・保存・解放 → 必要なら理解モデルで確認 → 対話モデルが説明」とする。
- 受付判定は、常駐中の重み、入力の展開量、KV キャッシュ、生成の作業領域、ロード時ピークを合算し、P0 で測った実測値と安全係数で行う。トークン数は実行エンジンと同じ tokenizer・chat template で数える。
- 実行直前に空きメモリを再確認し、他アプリの使用で足りなければ待機・停止・再計画を提示する。
- **GPU タイムアウト対策（RTX Spark 固有）：** 長い生成は区切り（動画ならセグメント、音声なら文単位）で実行し、各区切りの結果を保存する。ドライバのリセットや無応答を検知したら、ジョブを失敗として記録し、エンジンを再起動して保存済みの区切りから再開を提案する。盲目的に自動再試行しない。
- **電源：** ノート型でバッテリー駆動中は、長い生成の前に警告する。構築時の測定は AC 電源接続時に行い、測定時の電源状態を記録する。

## 9 ジョブ・記録・成果物

- ジョブは ID、環境・構成版、状態（待機／ロード中／処理中／保存中／完了／取消／失敗）、進捗、結果、エラーを持つ。
- 進捗はエンジンが返す値だけを表示し、根拠のない割合や残り時間は出さない。
- UI を閉じても制御サービスが動いている間はジョブを続け、再接続時に状態を照合する。制御サービスが落ちた場合、途中のジョブは「中断」とし、保存済みの区切りだけを再利用できる。
- 修正は新しい版として保存し、原素材や以前の生成物を上書きしない。
- **共通成果物フォルダ：** 四環境の生成物と E1 の回答・要約を一つのフォルダに保存し、各ファイルに由来情報（ID、版、内容ハッシュ、種類、作成日時、生成元環境、モデル・設定、元素材）を JSON で付ける。UI で一覧・プレビュー・添付ができる。
- 受け側環境で読めない形式・大きさは、理由を示して読み込みを止める。変換が必要なら方法を示し、承認後に派生版として保存する。
- 由来情報や以前の出力はデータとして扱い、命令や権限として扱わない。

## 10 安全性とプライバシー

- 素材や会話を外部へ送らない。クラウドへの代替処理はしない。
- ローカル API はループバックのみ。WSL2 を使う場合もポートを外部に公開しない。
- 取得したモデル・コードの実行権限を絞り、素材内の文章を命令として扱わない。パス逸脱や過大な展開を防ぐ。
- **声と肖像：** E3 の参考音声、E4 の参考動画・画像に実在の他人の声や顔が含まれる場合は、本人の同意を得ているかを確認する表示を出す。生成物の由来情報に「AI生成」を記録する。
- ログに素材の内容を必要以上に残さない。

## 13 ライセンス

- 本ツールは個人利用に限る前提で候補を選ぶ。配布や商用利用に広げる場合は、全カタログ構成のライセンスを見直す。
- LTX-2.x は年収1,000万ドル以上の組織に有償ライセンスが必要。FLUX.1 dev は非商用。Wan 2.2 は Apache 2.0。
- 取得前にライセンスと利用条件を画面に表示し、認証が必要なモデルはユーザーが手続きする。

## 14 リスクと対策

| リスク | 対策 |
|---|---|
| RTX Spark 向けのソフトが揃っていない（llama.cpp CUDA ビルド、ComfyUI、TTS、動画エンジンの Arm64 Windows 版） | P0 で最初に確認。WSL2 案を並行して試す。どちらでも動かない環境は時期をずらす |
| プレビュー段階のドライバ・CUDA の不具合（GPU タイムアウト等） | 版を固定し、区切り実行と保存で被害を限定する（8章） |
| llama.cpp の動画入力で音声まで聞けるモデルが限られる（LFM3-Omni のみ） | 3.2節の分離方式と比較し、対応モデルの追加を追跡する |
| モデルの入れ替わりが速い（LTX は2→2.3→2.5が約7か月） | カタログをデータとして分け、四半期ごとに見直す |
| 統合メモリで上限を厳密に強制できない | 実測ピーク×安全係数で受付し、厳密保証はしないと明記する |
| ディスク不足 | 構築前の容量確認と、環境ごとの分割導入 |
| 日本語の品質不足（特に TTS・音声理解） | P0 で日本語課題を用意して確認し、不足なら候補を変える |

## 15 P0 で確定する事項

- 実行基盤（WSL2／ネイティブ）と、各エンジンの動作可否。
- GPU から確保できる実際の上限と、WSL2 を使う場合のメモリ設定。
- 各環境の標準構成・軽量構成と、そのピークメモリ・速度。
- UI を既存 OSS で済ませるか、独自に作るか。
- 品質課題（日本語を含む）と合格基準。
